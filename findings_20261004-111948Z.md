# Findings: syncing two 4.5 TB USB drives (2026-10-03 to 10-04)

This covers a real two-way sync of `/run/media/ace/Movx/acex` on a Linux machine with `sftp://ace@qube/Volumes/Movx/acex` on a Mac (qube). Both are spinning USB disks formatted exFAT, and the network link is Wi-Fi through Tailscale. The trees hold about 10,000 folders and 46,000 files.

## What happened

| Run                           | Time        | Copied                     | Notes                                  |
| ----------------------------- | ----------- | -------------------------- | -------------------------------------- |
| 1: old build                  | ~10 h, stopped | ~375 GB from qube       | Mostly moved files sent again          |
| 2: with reuse and walk fixes  | 2 h 5 min   | ~75 GB, 1,444 files        | Clean; walk took under 40 min          |
| 3: timing run, nothing to do  | stopped at 31 min | nothing               | qube's disk was the bottleneck         |

## Problems found and fixed

### 1. Mac litter blocked SWAP cleanup (commit `7d9087d`)

A Mac writes `._<name>` AppleDouble files beside anything it touches on exFAT, so a SWAP folder a Mac had seen never became empty, and copies ended with `cleanup: io_error` (the copies themselves were fine). SWAP cleanup now deletes `._*` and `.DS_Store` before removing the folder. Scenario S-18.

### 2. Moved files were sent again in full (commit `a75c661`)

The biggest problem. qube's library had been reorganized (shows moved into `shows/<Show>/Season NN/`, movies into their own subfolders, many renamed). KitchenSync saw each move as a deletion plus a new file, so this drive set its copy aside in BAK and downloaded the whole file again. Of the ~375 GB copied in run 1, about 281 GB was files whose exact-size twin was set aside on this drive in the same run. Another ~61 GB was real changes: for example, `Nope.2022...mkv` differed only from byte 57 (header details rewritten by a media manager, same size), which still means sending the whole file.

Fix: copies of files of 1 MiB or more wait until the walk ends. Then, if this run set aside a file on the receiving peer with the same size, the same date (within 5 seconds) and three matching 64 KiB samples (start, middle, end), that file is renamed into place instead of transferred. The output shows `M<peer> <path>`. A reused file goes straight from BAK to its final path (never through SWAP `new`), so an interrupted run cannot mistake it for a cut-short transfer. The manifest records the BAK path in a new optional `origin` field, and rollback moves reused files back to BAK in a first pass before restoring. Tested over SFTP against the ephemeral server. Scenarios S-19 to S-21.

Known limit: only files set aside in the same run are reused. Run 2 still downloaded ~75 GB because run 1, which was stopped, had already set those originals aside.

### 3. Every run rewrote every manifest (commit `8e8f438`)

Each run refreshed `last_seen` on every entry, so every folder's manifest was rewritten and the old one archived to a new `BAK/<ts>/` folder. That is about ten extra filesystem calls per folder per peer, run one at a time on the walk thread, and on exFAT with 128 KB clusters each archived 2 KB manifest plus its folder costs ~256 KB, roughly 2.5 GB of clutter per run per drive. In run 1 the walk managed about 0.9 seconds per folder, against about 0.03 seconds for a plain `find`.

Analysis: `last_seen` is only used to decide whether a missing file was deleted (seen after its newest edit anywhere). Refreshing it every run changes a decision in only one rare conflict, and keeping the older value errs toward copying the file back rather than deleting it. A single run timestamp at the sync root was also considered; it works but needs extra rules for skipped folders, excludes and nested sync roots. The user chose the simpler rule.

Fix: an unchanged entry keeps its manifest line, so an unchanged folder is not written at all. `last_seen` is refreshed only when the file changed or when it is not later than the file's own date (protects against future-dated files). Each folder's listing, manifest and `.kitchensync/` listing are now read at once; repair and BAK cleanup run only when that listing shows something to do. Scenario S-22 checks that a second run over an unchanged tree changes no metadata.

## Open problems

### SFTP request timeout skips folders on a slow server

Each SFTP request gives up after 60 seconds (`session.set_timeout` in `code/src/transport/sftp.rs`). In run 3 a manifest read on qube waited behind a large folder listing and failed, so the whole folder was skipped for that run (`manifest read failed ... io_error: Timeout`). That is safe but wrong: a slow server should not cause skips. The SSH keep-alive already detects dead connections, so the request limit can be much longer.

### qube's disk limits the walk over SFTP

During run 3 this machine's disk was idle and only ~10 KB/s came from qube, while all four `sftp-server` processes on qube sat in disk wait. qube's USB disk managed about 50 to 100 small reads per second (0.2 to 0.4 MB/s), typical of a spinning disk seeking. macOS's `sftp-server` looks up every entry of a folder one by one, and on this exFAT disk each lookup is a seek. A local walk on the Mac uses `getattrlistbulk` (one call per folder), which is why a plain `find` on qube covers the tree in about 6 minutes. Run 2's walk was likely faster than run 3's because qube still had the tree in its cache from run 1. Spotlight indexing was also enabled on the drive, with idle `mdworker` processes present.

## Recommended next steps

1. Continue on qube (a Mac): clone the repo, `brew install uv`, put the Rust toolchain under `./tools/rust/` (see `specs/DEVELOPMENT.md`), run `uv run code/setup-cross-tools.py`, then `uv run code/build.py`. The Mac and Windows binaries in `released/` predate the three fixes above.
2. Raise the SFTP request timeout and add a test.
3. Run the sync from qube, so qube's slow drive is the local peer: `kitchensync.mac /Volumes/Movx/acex sftp://ace@<linux host>/run/media/ace/Movx/acex`.
4. Consider `mdutil -i off /Volumes/Movx` on qube so Spotlight does not compete for the disk.
5. Time a second, no-changes run to measure the walk on its own.

## Ideas for later

These came up during the work and were not pursued. Each is a direction, not a design.

- **Reuse across runs.** Reuse only matches files set aside in the same run, which is why run 2 still downloaded ~75 GB. Files set aside recently (for example, by the newest run in `.kitchensync/runs.txt`) could also be candidates, with the same size, date and sample checks.
- **Lighter copies for small files.** Each copy costs about a dozen filesystem calls over SFTP (SWAP recovery checks, staging, renames, setting the date, cleanup). Thousands of small `.trickplay` images moved at about 6 MB/s. A new file with no existing destination might skip some of those steps safely.
- **Held copies give up overlap.** Copies of 1 MiB or more now wait for the walk to end. That is fine with a fast walk, but on a slow tree the copy work no longer overlaps the walk. Starting held copies whose source cannot match any displacement (no displaced file of that size on the peer once the walk passes a point) is one possible refinement.
- **Dry runs do not predict reuse.** A dry run prints `C` for copies a real run may turn into `M`, so it overstates the work. It could plan reuse from the would-be displacements, at least for displaced files (directories would need listing).
- **Read-ahead may hurt spinning disks.** Eight prefetch threads list folders ahead of the walk, and on a hard disk that jumps between folders and adds seeks. Fewer threads per peer, or per-peer tuning, might be faster on hard disks.
- **Bulk listing over SSH.** When the server allows running commands, one remote command could list a whole tree with names, sizes and dates, avoiding the per-entry lookups of `sftp-server`. Portability across macOS, Linux and Windows servers is the hard part.
